篇章 4：數值與玩法篇 ｜ 配點、加成能力與 Type-12 契約

配點不是「伺服器算好送給客戶端」而已。LM 實驗室受控客戶端副本的能力面板由客戶端自行推導—— 它用自己的職業基礎表、自己從 Type-12 算已配點、自己決定按鈕何時亮。 本篇記錄四個訊息（10 / 12 / 14 / 15）的精確欄位契約， 以及一個「伺服器每個回應都合法、畫面卻顯示 −30」的實例如何被逐步拆解。

⚠️ 適用前提與實驗邊界

本文假設讀者已具備受控本地客戶端副本的 ARM64 靜態分析環境（Unpacked ELF）與自有測試服務端。 未對第三方後端資料庫進行入侵或直接操作；文中提到的資料庫，均為自建測試儲存， 案例中的等級、點數與六維數值為實驗室測試角色的量測值。 欄位語意與公式僅適用於本專案所分析的客戶端版本，不得直接套用到其他版本。

證據標記：【本地觀測】＝自有環境量測到的事實；【推論】＝由觀測推導、尚未直接驗證； 【未驗證】＝尚無證據支持的假設。職業一律以「職業基礎值」表述，累積型道具以「累積幣」表述，不綁定特定道具或職業名稱。

手機閱讀：寬表格與程式碼可在各自區塊內左右滑動。

二、客戶端自己算了什麼（這才是重點）

1. 「加成能力」文字 ＝ 15.field1 − Σ(CharacterInfo.m_totalStat − classBase)

客戶端不信任伺服器送來的「剩餘點數」。它以 Opcode 15 的 field 1（總池）為被減數， 減去它自己由 Type-12 推導出的已配點總和（六維總值 − 客戶端內建職業基礎表）。 因此同一個畫面值，可能由完全不同的（我方欄位, 客戶端狀態）組合產生——這就是本案最大的陷阱。 【本地觀測】面板數值完全由客戶端這條算式決定，伺服器無法從畫面反推它算對了沒有。

2. 面板重畫的觸發條件 ＝ Type-12 的「新舊 base 不相等」

CharacterInfo::OnStatNoti 會比較新舊 BaseStat，只有不相等時才派發 Event 0x71c 觸發六維文字重繪。若 field 5 永遠送職業基礎值（例如某職業 STR 基礎值 16）， 伺服器就算送出正確的總值，畫面也不會更新。

3. 「決定能力」按鈕 ＝ 剩餘恰為 0 才亮

客戶端原生硬編：剩餘點數 == 0 才啟用按鈕（大於 0 或小於 0 一律置灰）。 常見體感「+1 就能按」是因為每級只給 1 點；若測試角色一次拿到多點，就必須點完才會亮。

4. 降配點是不可能的操作

減號按鈕閘門要求 currentStat > baselineStat 才啟用， 因此客戶端不可能產生「低於目前總值」的提案。若收到此類封包（異常封包或非預期的重放）， 伺服器應以 Result = 6 (Fail_LowStatCount) 拒絕，並在 10 回應中把 keys 夾止在職業基礎值。

三、實例拆解：−30 的誕生與終結

症狀：測試角色等級 82（點數池 32、已配 31），面板顯示 加成能力 −30， 且完全重啟 App 後仍重現（代表不是客戶端殘留）。

階段進世界 Type-12客戶端自算已配我方 15.field1畫面
修正前（舊版）16（捕獲模板值）(16−16)+(16−16)=00（誤當 remaining）0　← 假象吻合
修正 Type-12 後21 / 42（本角色真值）(21−16)+(42−16)=311（仍誤當 remaining）−30　← 真因暴露
修正 15.field1 後21 / 423132（總池）+1　← 正確
最大的教訓：舊版「看起來正確」是巧合

舊版之所以顯示 0，是因為進世界的 Type-12 送了固定的捕獲模板值 16， 讓客戶端算出的已配點剛好為 0，於是 0 − 0 = 0。 當我們把 Type-12 修成正確的本角色值（21/42）後，客戶端終於算出真實的已配 31， 隱藏已久的 15.field1 語意錯誤才被暴露出來。 「改了 A 之後 B 才壞」往往不是 A 的錯，而是 B 一直是錯的、只是以前被掩蓋。

四、進入世界的第一幀，決定一切

客戶端的 ElixirSimulator 並不是常駐監聽網路，它在使用者開啟能力面板時 才向 CharacterInfo 取樣，而 CharacterInfo 的六維來自進入世界時的 Type-12。 若該幀仍使用捕獲模板的舊值（例如其他角色的 16/11/16），模擬器的基準線就會被鎖在錯誤值上， 之後所有配點計算全部偏移。

✔ 正確實作

進入世界的 Type-12 必須以本角色的已配點總值改寫 field 1 與 field 5 （我方由准入階段讀取角色配點後帶入），生命值欄位照舊、其餘幀與順序不動。 驗收斷言：非零配點角色必須等於「21/11/42/7/8/8」且明確不等於職業基礎值。

五、累積幣欄位（Type-920）的零狀態

當前服務端沒有任何累積幣的產出機制，因此協議上必須維持零值： current = 0、cumulative = 0、level = 0， 僅保留 _max 層（1200000 / 200，該副本的常數）。幣數換算為 ceil(current / 6000)； 級距由 level 驅動（0 灰、1 橙、2 綠、3 金、4 最高階外觀）。 不要用經驗值推導累積幣——那會讓尚未實作的機制長出假數值。

六、方法論：這次為什麼能一次修對

  1. 先量測，不改線。我們在中間版本加了「唯讀診斷」：把客戶端送來的 10/14 內容解密後印出。 第一次就證明了 proposed 是絕對值（21/42），而不是我們假設的「基礎值＋待配置」。
  2. 唯讀診斷不等於免審查上線。在自建環境中解析失敗只記 undecodable、不更改處理分支；部署與日誌內容仍須授權並經資料最小化檢查。
  3. 三點數據勝過三次猜測。把 D1/D2/D3 三個時間點的我方送出值＋客戶端畫面值並列， 讓受控副本的靜態分析者能直接反解出顯示公式。
  4. 完整測試套件是最後防線。本輪兩次「局部自測全綠、全套爆掉」都是舊斷言洩漏： 被改掉的行為仍被某個未跑的套件釘住。修復不是改測試，而是刪除錯誤契約、更新為正確契約。

七、可施工的落地公式（速查）

# 配點落地（C2S 14 / C2S 10 field2 皆為絕對目標總值）
delta       = proposed - 我方目前已配點總值        # 對「總值」取差，切勿再對職業基礎值取差（會重複累加）
newAllocated = 已配點 + delta                     # 等價於 proposed - classBase
if delta < 0: return Result = 6                  # 降配點＝非法

# 10 ACK（S2C）
field1      = 我方總值 + delta  ( = proposed )
keys 41..46 = classBase + max(0, delta)           # 夾止，永不低於職業基礎值
keys 17/18/21 = 裝備 HP/MP/AC；keys 1/2/8/9 = 0

# 15 ACK（S2C）——最常寫錯的一格
field1      = 總點數池 totalAvailable             # 不是 remaining！
field2      = spent
field3      = 完成時間（可 0）
field8      = 50                                  # 單項加點上限
field10     = totalAvailable

# 14 成功後的幀序
12 (field5 = 已配點總值) → 14 (result=1) → 15

八、紅隊觀察 → 藍隊驗證與遙測

本節把「客戶端自算面板」翻譯成防守語言：左欄部分操作是授權實驗室可設計的對抗檢查， 並非本文聲稱已對外部系統執行的攻擊；右欄是建議的驗證與遙測，不代表已全部實裝。 −30 是自建環境的實測畫面誤差，不是第三方系統的資安事件。

紅側：重建端可觀察／可推論的行為藍側：真值來源、驗證與遙測
面板形狀推論：從 10/12/14/15 的欄位組合反推伺服端語意，再用自製回應觀察面板如何反應，嘗試讓 UI 顯示任意剩餘點數 伺服器是唯一真值來源：客戶端送出的 10 field2／14 field1 一律視為「提案」；面板值僅供顯示，永不作為授權依據。遙測：以伺服端狀態（spent/remaining）為準的對帳，不採信 UI 回報值
提案值探測：送出極大值、負值、低於目前總值，或連續送出多筆以觀察邊界行為 擁有權＋邊界：每筆提案必須通過角色／工作階段綁定的擁有權檢查；delta < 0 一律 Result = 6 拒絕，單項上限與總池上限雙重檢查，回應顯示值夾在職業基礎值以上。遙測：越界 delta 拒絕率、單項上限觸發數
重送與交錯：同時送兩筆配點、不等 ACK 反覆重送，觀察是否重複計點或產生負剩餘 提交序列化＋冪等：以期望版本／序號對齊，舊序號丟棄、重複請求合併。遙測：每角色配點請求速率、重複請求比例、序號衝突拒絕數
干擾幀序：吞掉或延後權威快照幀，觀察客戶端基準是否被鎖在舊值、畫面是否停在過期數字 固定幀序 12 → 14 → 15，提交前先送權威快照；快照與提交綁定同一版本。遙測：幀序偏離率、基準未更新即提交的次數
高頻請求：以自動化方式大量送出配點請求，觀察點數池與狀態是否仍自洽 速率限制＋稽核：每次配點寫入 audit（前後總值、delta、提案值、來源訊息、序號、工作階段），定期對帳。遙測：每分鐘配點請求分布、audit delta 不匹配數、總池為負的次數
一句話總結

畫面對 ≠ 授權對。凡是「由客戶端算給人看的數字」，都必須能在伺服端用稽核紀錄獨立重算一次； 兩邊對不上時，以伺服端紀錄為準，並把「對不上」這件事本身當成告警，而不是當成 UI 的小瑕疵。
