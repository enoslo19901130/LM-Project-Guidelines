篇章 2：會話篇 ｜ 身份鏈、用途隔離與版本漂移

同一條「登入到拿到可進世界憑證」的鏈，在兩個客戶端版本之間可能少一站、也可能多一站；同一筆邏輯欄位，在不同版本的 wire 上還可能掛著不同的不透明鍵名。本篇以 LM-Project 自有測試環境的唯讀流量與靜態資產為例，整理三件事： 會話鏈的形狀、最容易被誤判為「已授權」的三種訊號，以及服務端要如何在不放寬認證的前提下同時相容多個版本。

⚠️ 適用前提與實驗邊界

本頁是 LM-Project 自建實驗室的工程案例研究：觀察對象是受控的本地客戶端副本與自建隔離的測試服務端； 既有唯讀流量僅作對照，未對第三方後端資料庫進行入侵或直接操作。文中所有 token、帳號、裝置識別與欄位鍵皆去敏或遮罩， 數值與站點順序只適用於其來源版本，換版本請重新驗證。

證據強度標記沿用全站慣例：【本地觀測】＝自有環境量測到的事實；【推論】＝由觀測推導、尚未直接驗證； 【未驗證】＝已提出或已實作但尚未證明有效。

手機閱讀：寬表格與程式碼可在各自區塊內左右滑動。

一、會話鏈的形狀（本地觀測）

在自建環境中，客戶端從「按下登入」到「取得可進世界的憑證」，會經過多個站點；下面是去敏後的形狀示意 （站名以用途表述，非實際路徑字串）： 

[登入頁 WebView] --表單提交--> [帳密驗證站] --回呼攜帶短期憑證--> [會話交換站] --會話識別-->
[會話完成站] --取得登入狀態--> [認證型別查詢站] --（必要時）--> [二次認證：開始/完成]
--> [憑證發放站 authn] --> [大廳/世界准入]
站點（用途）輸入輸出藍隊重點
登入頁（WebView）畫面與指令碼表單提交頁面來源與回呼白名單
帳密驗證站帳號與密碼雜湊（不落明文）短期憑證雜湊、速率限制、錯誤不回傳帳號是否存在
會話交換站短期憑證會話識別（不透明）一次性、綁定來源、可撤銷
會話完成站會話識別登入狀態狀態不得由客戶端自報決定
認證型別／二次認證站登入狀態一次性驗證碼與其交換結果單次碼、逾期、用途隔離
憑證發放站（authn）登入狀態（＋二次認證結果）可帶往大廳／世界的憑證只由已驗證結果產生；不得匿名升格

【本地觀測】版本漂移：兩個受測版本在一次登入窗內，站點集合並不完全相同——其中一版在登入前多了一次 「供應商憑證交換」（provider grant）呼叫，另一版沒有；後續站點的欄位鍵名也不同（見第三節）。 單一版本的單次擷取不足以推論另一版本一定沒有該站點；本頁把它當成「版本間流程會漂移」的實例，而不是通則。

二、三種最容易被誤判為「已授權」的訊號

訊號紅隊視角藍隊控制
格式合法（欄位齊、型別對） 把請求組得「像」正常客戶端，觀察服務端是否直接相信欄位內容 每個站點重驗身份、資源歸屬與一次性；格式正確 ≠ 操作授權
畫面成功（客戶端顯示已登入） 客戶端畫面由本機狀態驅動，與後端授權可以不同步 以服務端結果為權威；畫面成功不作為授權或稽核依據
客戶端自報值（應用識別、版本字串） 應用識別與版本都寫在客戶端內、可被重放或改寫；同一應用識別可能跨版本共用 只當相容性選擇鍵：缺漏、未知或彼此衝突 → 明確拒絕；永不作為帳號或已驗證身份，也不作為身份欄位的退路

三、用途隔離：供應商憑證 ≠ 玩家會話

最危險的形狀是：某個「供應商交換」站回傳的憑證，因為實作方便，被下游拿來換取玩家的登入憑證、二次認證或大廳資格。 一旦如此，未經驗證的客戶端自報值（如應用識別）就等於走進了玩家憑證鏈。【本地觀測】在自建環境中， 供應商交換與玩家會話在資料模型上可以只差一個用途（purpose）與主體（subject）欄位——這個差異肉眼幾乎看不出來。

✖ 反模式：只改名字的隔離

把供應商憑證的用途「改名」成玩家會話、或讓下游「沿用既有派生路徑」取得玩家憑證，等於沒有隔離。 隔離必須在每個消費者上成立：憑證發放、二次認證、大廳與世界准入都要各自檢查用途與家族，而不是只檢查簽章或格式。

控制要求
用途與家族供應商憑證具獨立 purpose／family；不可換取玩家憑證、二次認證或大廳／世界資格
一次性與期限交換碼單次使用、短效、可撤銷；重放與逾期明確拒絕
產生條件玩家會話只由「已驗證的帳密」或「已證的供應商身份結果」產生；沒有後者契約時，沿既有登入驗證，不得發明匿名升格
撤銷語義撤銷覆蓋憑證家族；登出／到期後在途身份不得再用

四、版本漂移：為什麼需要「回應層 Profile」

【本地觀測】同一筆邏輯欄位在兩個版本的不透明鍵名不同（欄位鍵本身是被混淆的固定字串）；同一條鏈在其中一版多了一站。 這代表服務端不能用「一組硬編碼欄位」同時服務所有版本，也不該把版本判斷散落在各處 if。 可行的工程形狀是：把「某個客戶端選擇鍵＋版本」對應到一組回應層設定（Profile），由外部設定檔驅動、可熱重載， 且 **只決定回應的欄位、型別、別名、封套與非敏感常數**。

規則理由
選擇鍵只作選擇應用識別／版本字串可被重放；不可作為身份、不可 fallback 到身份欄位
未知或衝突 → 明確拒絕回固定原因的 4xx；不得「回預設成功」或沉默降級
Profile 不改判認證成功／失敗、token、主體、有效期、二次認證能力不得由設定偽造或改判
熱重載要原子完整解析與驗證後整份發布；壞檔保留上一版良好設定；單一請求不混用兩代設定
回退要單檔可還原還原設定檔並重載後，新家族回到原行為；既有家族沿原快照到登出／到期
稽核要可追溯記錄路由、Profile 版本、設定內容雜湊與選擇原因（遮罩）；不記憑證、完整請求／回應或帶 token 的路徑
✔ 一句話原則

Profile 只能讓「已授權的業務結果」用不同版本看得懂的方式呈現；它不能讓未授權的請求變成通過。

五、藍隊檢查清單

#檢查通過標準
1客戶端自報值的處理僅作選擇鍵；未知／衝突回固定原因；無身份 fallback
2會話與選擇鍵的綁定同一會話家族沿固定 Profile 快照；登出／到期後失效
3供應商憑證用途隔離無法換取玩家憑證／二次認證／大廳或世界資格
4一次性與重放交換碼單次、短效、逾期與重放皆拒絕
5本地登入仍可用設定不得把失敗改判成功；有效帳密流程不受 Profile 影響
6設定熱重載有效改檔生效、壞檔拒絕且保留上一版；還原單檔可回退
7稽核欄位路由、Profile、設定雜湊、選擇原因可查；無憑證外洩
8錯誤路徑錯序、缺欄、衝突都有可追溯的拒絕原因；不以空物件冒充成功
9重啟語義重啟清空記憶體會話；文件不宣稱可保留在途登入
10版本新增流程新版本先補「選擇鍵↔版本↔回應形狀」證據，再以合成 fixture 驗證，最後才用真實來源驗收

六、待驗與延伸

  • 登入持續性【未驗證】：官方行為是登入後保留、按「登出」才需重新登入；自有重建版在登入鏈未完整前，無法判定是否每次啟動都需重打帳密。列為登入鏈打通後的第一個驗收項。
  • 站點集合的版本差異【本地觀測，單次擷取】：僅代表兩個受測版本各一次登入窗；需更多樣本才能區分「版本差異」與「條件差異」。
  • 心跳與超時：屬會話狀態機的一部分，本頁不展開數值；數值需以各自版本的實測重新驗證。
  • 供應商回應的消費欄位：客戶端實際讀取哪些回傳鍵，屬下一輪靜態取證題目；在取得清單前，服務端回應形狀只能以最小必要集合處理。
