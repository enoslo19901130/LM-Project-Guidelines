LM 客戶端 Wire 協定與 Google Protobuf 快速入門指引

專案命名：LM-Project ｜ 專案發起人：Enos
為人類工程師與自主 AI Agent 打造的底層二進位通訊入門：從位元運算、套娃（Length-delimited Nesting）模型、容錯與 Fail-Closed 紀律，到本地授權樣本的靜態描述符復原、實驗室流量觀察與 Wire 處理器開發規範。

⚠️ 閱讀前提與專業邊界聲明 (Prerequisites & Boundary Notice)

適用對象前提：本指引假設讀者已熟悉 C/C++ 二進位結構、序列化與網路框架，並願意在合法持有的本地樣本與自建隔離實驗室上做靜態分析與流量觀察。

分析範圍聲明（高層概述）：本篇提到的「描述符復原」，指的是對自己合法持有的本地客戶端樣本做唯讀的靜態結構分析（例如從共用函式庫的符號與內嵌描述符資訊比對欄位編號與 WireType），以及對自建隔離實驗室伺服器所產生流量的觀察與比對；本庫亦保存歷史封包擷取與唯讀觀測記錄作為分析素材。本篇不提供、也不需要任何繞過保護、破解授權或取得他人資料的步驟。

邊界與資料來源：文中的資料庫讀寫與角色狀態，均指自建隔離實驗庫；客戶端資產來自受控本地副本，封包對照包含自建環境與既有唯讀紀錄，來源不可混為同一種實測。本專案未對第三方後端資料庫進行入侵、直接操作或資料擷取。本地與封存觀測僅用於理解協定契約，不能據此推論任何第三方系統的安全性；欄位結論綁定本次分析版本，換版本必須重新驗證。

手機閱讀：寬表格與程式碼可在各自區塊內左右滑動。

⚡ 第一章：根本原理：傳統二進位在 Protobuf 時代的典範轉移

在接手 LM 服務端的二進位協定工作前，必須先徹底洗去「把 C 結構體原封不動丟上線」的傳統封包處理思維：

❌ 傳統封包：固定記憶體偏移量 (Fixed Byte Layout)

傳統 C/S 架構通常直接將 C 語言結構體（struct）以位元組流發送：

// 傳統 C 結構體
struct CharacterPacket {
    uint8_t  opcode;     // 1 byte (偏移量 0)
    uint32_t charId;     // 4 bytes (偏移量 1~4)
    uint16_t x;          // 2 bytes (偏移量 5~6)
    uint16_t y;          // 2 bytes (偏移量 7~8)
};

致命缺陷（骨牌崩潰效應）：

  • 雙方代碼必須 100% 絕對二進位對齊。
  • 只要對端在 charId 之後插入一個 4-byte 欄位 worldId，本地端如果沒有同步更新，後面讀取的 x 與 y 就會全部錯位，角色座標飛越或進程直接崩潰。

✅ 現代封包：Protobuf 欄位編號與線型別

LM 受控客戶端的通訊採用 Google Protocol Buffers。封包不依賴固定欄位偏移；線格式可讀出欄位編號與 WireType，欄位名稱、語意和必要性仍須依 schema 或獨立證據判斷：

// Protobuf 概念資料流
[Key: 欄位1+數值類型] -> [數值: 1002]
[Key: 欄位2+字串類型] -> [長度: 6] -> [數值: "起始城"]

格式相容性與限制：

  • 欄位順序無關：客戶端先傳欄位 2 再傳欄位 1 完全合法。
  • 省略需按契約判斷：部分欄位可省略，但零值與缺席不必然等價；必要欄位缺席時，業務層必須拒絕。
  • 未知欄位有界跳過：新版本客戶端增加欄位 99 時，舊版伺服端在該欄位語法有界（長度可被精確計算）的條件下能跳過它，不會因為「看不懂」而崩潰——但這只是格式相容性。若長度越界、WireType 非法或游標無法對齊，必須有界地拒絕該封包；格式通過也不代表業務層授權通過（見第五章心法 2、第十章、第九章 Q2）。

🧬 第二章：底層傳輸原理：Tag、WireType 與 Varint 變長位元解密

在實體網路線（Wire）傳輸時，Protobuf 是如何讓接收端知道欄位編號與數據類型的？答案在於開頭的 Key。

Key = (Field Number << 3) | WireType

這個位元公式說明：Key 的低 3 位元（0~2 bits）代表資料形態（WireType），其餘高位元向右位移 3 位就是欄位編號（Field Number）。

WireType 類型名稱 對應資料型態 底層讀取方式與特徵
0 Varint int32, int64, uint32, bool, enum 變長整數編碼。每個 byte 僅用低 7 位元儲存數值，最高位元（MSB）為 1 代表後續還有 byte；為 0 代表結束。數字越小佔用位元組越少。
1 64-bit fixed64, sfixed64, double 固定長度，直接讀取接下來的 8 個位元組。
2 Length-delimited String, Bytes, 嵌套子結構 (Embedded Message), Packed 陣列 長度前綴。先讀出一個 Varint 得到長度 $L$，接下來精確讀取 $L$ 個位元組作為內含資料。
5 32-bit fixed32, sfixed32, float 固定長度，直接讀取接下來的 4 個位元組。

🔢 實戰示範：數字 300 是如何被 Varint 編碼成 AC 02 的？

  1. 十進位 300 轉為二進位：0000 0001 0010 1100。
  2. 從低位開始，切分成 7 位元一組：
    • 第 1 組（低 7 位）：010 1100 (十進位 44)
    • 第 2 組（高 7 位）：000 0010 (十進位 2)
  3. 加上最高位標誌（MSB）：
    • 第 1 組後面還有資料，MSB 補 1：1010 1100 ➔ 十六進位 0xAC
    • 第 2 組是最後一組，MSB 補 0：0000 0010 ➔ 十六進位 0x02
  4. 最終在二進位流中呈現：AC 02（僅用 2 個 bytes 就傳輸完成，省下大量頻寬！）。

🪆 第三章：核心架構模型：俄羅斯套娃 (Matryoshka) 深度解構與視覺化

初學者最常產生的疑惑：既然上面的 WireType 表格只有數字、字串和二進位 bytes，那像「角色資訊裡面包著裝備清單、裝備清單又包著單件道具」這種複雜物件是怎麼傳輸的？

答案就是「套娃（Matryoshka）」機制！

💡 套娃真理
在 Protobuf 的底層傳輸世界裡，根本沒有「物件（Object/Message）」這個獨立類型！所有的物件在被裝入外層時，都只是被序列化成一段 WireType 2 (Length-delimited Bytes)。只要外層標記長度，裡面就是一隻獨立的子套娃！
最外層套娃：NotifyStat（合成示意：世界廣播通知，總長度 18 Bytes）

[Key: Field 1 + Type 0] [Value: 角色流水號 10088]

中層套娃：Attributes 屬性清單容器 (外盒標籤: Field 2, WireType 2, 長度: 8 Bytes)

外層封裝：[Tag: 0x12] [Len: 0x08]（告訴解析器接下來 8 個字節是中號盒子內容）

最內層小娃娃：單一屬性 Attribute (長度: 4 Bytes)

[Key: Field 1 (屬性代碼)] [Value: 21 (代表物理防禦 AC)]

[Key: Field 2 (計算結果)] [Value: 7 (有效防禦值)]

💥 實驗室踩坑紀錄：Type-12 物理防禦 (AC) 消失事件

在隔離實驗室的本地測試中，伺服器端已下發穿戴防具後的 AC（7），但客戶端面板上的防禦數字仍卡在初始值 10。

根本原因：工程師在組裝封包時，把最內層的「小零件」直接拋進了最外層的大箱子，中間忘記套上「中層盒子」（缺少了外層 Field 2 的 WireType 2 長度封裝）！

客戶端的 C++ 反序列化器打開外箱時，原本期待看見一個標註長度的中號盒子，打開才拿零件；結果一開箱發現零件散落一地，解析器直接回報格式毀損並整箱丟棄，面板只好回退顯示本地舊數據。

重要提醒：「面板數字有變化」不等於伺服器端授權通過。客戶端顯示只是渲染層的回饋，權威狀態、持有權與冷卻計時一律以伺服器端判定為準——這一點在第十章的紅藍對照中會再具體說明。

🚀 第四章：快速切入四部曲：全流程標準作業指南 (SOP)

不論是人類工程師還是自主 AI Agent，當需要為伺服器新增、除錯或擴充任何通訊協定時，請嚴格遵循以下 4 步標準作業流程；這四步全部可在隔離實驗室與離線合約測試內完成，不需要接觸任何正式營運環境：

STEP 01 實驗室觀察與日誌定位 (Observe & Locate)

當玩家在受控測試用戶端觸發特定功能（如加點、喝水、穿脫裝備、丟棄道具）而伺服器無反應或報錯時：

  • 檢查伺服器端執行期日誌或控制台標準輸出。
  • 搜索關鍵標籤 world_frame_parse_reject 或 lobby_frame_parse_reject，捕獲精確 Opcode 與有界（bounded）Hex 內容： 
    [WARN] world_frame_parse_reject opcode=10 body_len=14 body_hex=120c0815100d18142009280a300b
  • 產出物：確認問題發生的通訊通道（Lobby / World 兩條獨立通道）、Opcode 編號，以及有界長度的封包 Hex 字串。
STEP 02 離線描述符復原與位元拆解 (Deconstruct & Identify)

利用核心公式與本地靜態分析產出的描述符目錄，將 Hex 翻譯為結構化欄位：

  • 位元拆解：利用 Key >>> 3 與 Key & 7，標註外層 Tag 與 WireType（如 12 = Field 2, WireType 2）。
  • 描述符比對：開啟由自持本地樣本的共用原生函式庫離線萃取之協定目錄（如 *-protobuf-catalog.json），依據 Opcode 或業務線索（例如屬性試算訊息）比對對應的 Message 描述。
  • 巢狀識別：確認外層是單純結構還是包裹了子 Message，查清每一層嵌套的 Tag 編號與型態。
  • 標註不確定性：凡未經實驗室流量或離線合約測試雙向證實的欄位，一律標記為「推測」，不得直接寫入正式邏輯。
STEP 03 編寫或擴充 Wire 處理器 (Implement Wire Handler)

在通訊層的 Wire 套件（實作上歸屬於 lmproject.lab.wire 這類自有實驗室命名空間）下編寫或修改對應的 *Wire.java：

  • 解碼端 (C2S Decode)： 採用 LmProto.Cursor + while(cursor.remaining() > 0) + switch(field)。 務必在 default 分支呼叫 cursor.skipWire(wireType)，讓語法合法但語意未知的欄位被有界跳過；但缺少必要業務欄位、狀態不符或未授權的動作必須 Fail-Closed 拒絕（見心法 2）。
  • 編碼端 (S2C Encode)： 採用 LmProto.fieldVarint()、LmProto.fieldString() 等拼裝；遇子結構必須使用 LmProto.fieldBytes(tag, childBytes) 進行套娃長度前綴封裝。
  • 業務銜接：Wire 類別僅處理二進位編解碼，解碼出的值物件（VO）傳遞給應用層處理；Wire 層不得直接觸碰任何資料庫或持久化設施，授權與持有權檢查一律在應用層與會話層完成。
STEP 04 註冊會話狀態機與離線迴歸 (Register & Verify)

將實作完成的 Wire 接回伺服器運行迴圈，並在離線合約測試與隔離實驗室內進行多重驗證：

  • 狀態機路由：在會話層的 frame 接收處理器中註冊該 Opcode 分發，並在分發前完成認證與狀態檢查。
  • 離線合約測試：建立或擴充單元測試，填入步驟 1 觀察到的 body_hex 進行位元組斷言，並額外加入「格式損毀」「缺必要欄位」「未授權動作」三組負向案例。
  • 全量迴歸：以專案既有的離線測試入口跑完整套檢查，確認全數綠燈後再進行下一步。
  • 實驗室驗證：於隔離實驗室重新執行動作，確認客戶端 UI 反應正確；此步驟僅作互動與渲染確認，權威狀態仍以伺服器端日誌與資料為準。

🏆 第五章：服務端開發五大黃金心法 (含 Before & After 代碼對比)

心法 1：欄位順序無關；必要欄位由契約驗證

❌ 錯誤寫法（線性順序讀取）

// 假設客戶端必先發 1 再發 2
long id = cursor.readVarint();
String name = cursor.readString();
// 若客戶端先送 2，直接死當錯位！

✅ 正確寫法（TLV 動態循環）

while (cursor.remaining() > 0) {
    long key = cursor.readVarint();
    int field = (int)(key >>> 3);
    switch (field) {
        case 1: id = cursor.readVarint(); break;
        case 2: name = cursor.readString(); break;
        default: cursor.skipWire(key & 7); break;
    }
}

心法 2：有界跳過（Fail-Safe Skip）與 Fail-Closed 的分界線

「看不懂就跳過」只適用於語法層面有界的未知欄位：也就是說，該欄位的 WireType 讓解碼器能精確計算出它的位元組長度，因此跳過後游標仍能對齊到下一個合法 Tag。這是 Protobuf 格式本身的相容性保證，不是安全保證。

實驗室教訓：先前伺服器端在解析兩個屬性試算 Opcode 時，遇到不認識的 Tag 便拋例外中斷連線。由於封包夾帶了客戶端自己的本地快取欄位，連續點擊加點的正常玩家被反覆踢下線——把「格式相容性」誤當成「一律不該斷線」，是典型的過度 Fail-Closed。
Fail-Closed 必須保留的閘門：以下四類情況必須拒絕並（必要時）中斷，不得以「跳過就好」帶過：
  • 線格式損毀：長度前綴越界、保留的 WireType 6 / 7、超過 64 位元的 Varint 或未終止值，必須立即中止解析；舊式 group WireType 3 / 4 雖屬 Protobuf 格式，但若本契約及解碼器不支援，也應明確拒絕。
  • 缺少必要業務欄位：語法合法但業務上必需的欄位（如目標物件識別碼、動作參數）缺席或為零值，必須拒絕該次請求並記錄，不能默默套用預設值執行。
  • 狀態不符：會話未認證、未進入世界、仍在交易／騎乘／死亡等不允許動作的狀態下收到突變型請求，必須拒絕。
  • 未授權或越權：請求涉及的物件不屬於當前角色，或要求的動作超出角色權限——必須拒絕，且此類事件應納入藍側告警（見第十章）。

一句話總結：WireType 層可以寬，業務與權限層必須嚴。寬是為了相容，嚴是為了安全。

心法 3：嵌套結構必須手動封裝長度（俄羅斯套娃規則）

只要是包在別人肚子裡的子 Message，在輸出給外層前，必須先算好長度，用 LmProto.fieldBytes(tag, childBytes) 封裝打包。

心法 4：輕量動態編碼（Wire Utility）勝過靜態代碼生成（protoc）

在契約持續微調的實驗室環境中，協定欄位經常調整。若使用 protoc 生成數千個 Java 類別，每次欄位微調就要耗費大量時間做全量編譯。自有的輕量 Wire 工具類允許直接在位元組陣列上組裝，零外部依賴、無額外物件配置負擔、改動可即時生效。

心法 5：最小合法注入原則（Minimal Conforming Injection）

絕對禁止「腦補欄位」。當描述符中可見欄位 1 到 20，但實驗室觀察到的合法請求只送欄位 1、2、10 時，伺服器端就只送這 3 個欄位。下發未經驗證的額外欄位，輕則使客戶端解析失敗、重者造成客戶端崩潰，也容易被防守方的封包形狀監控標記為異常。

🔬 第六章：經典實戰案例拆解：Opcode 10 與 Type-12 AC 逐 Byte 剖析

案例 A：Opcode 10 (屬性試算) 的 14 Bytes 合成樣本逐 Byte 拆解

以下為一份依據實驗室觀察到的結構、但數值已合成改寫的教學樣本（14 Bytes），用來示範拆解方法；它不是任何環境的實際流量，也沒有任何真實角色、帳號或位置資訊：

12 Key: F2, T2
0c Len: 12B
08 15 F1(STR): 21
10 0d F2(DEX): 13
18 14 F3(CON): 20
20 09 F4(WIS): 9
28 0a F5(CHA): 10
30 0b F6(INT): 11

逐字節反向解譯講義

  • 12：位元為 0001 0010 ➔ 低 3 位元 010 是 WireType 2，高位向右位移 3 位為 2 ➔ 「第 2 號欄位，長度前綴結構」。
  • 0c：十六進位 0x0c = 十進位 12 ➔ 緊接著後方的 12 個位元組全部是此子結構的內含資料！
  • 子結構內部：
    • 08 15 ➔ Tag 0x08 (Field 1, Varint), 數值 0x15 = 21（力量 STR）
    • 10 0d ➔ Tag 0x10 (Field 2, Varint), 數值 0x0d = 13（敏捷 DEX）
    • 18 14 ➔ Tag 0x18 (Field 3, Varint), 數值 0x14 = 20（體質 CON）
    • 20 09 ➔ Tag 0x20 (Field 4, Varint), 數值 0x09 = 9（精神 WIS）
    • 28 0a ➔ Tag 0x28 (Field 5, Varint), 數值 0x0a = 10（魅力 CHA）
    • 30 0b ➔ Tag 0x30 (Field 6, Varint), 數值 0x0b = 11（智力 INT）

關鍵啟示：若程式碼誤以為「封包開頭必為 Field 1」，就會在這個樣本上直接解析失敗。實際觀察到的請求並不送出 Field 1，而是直接送出 Field 2 巢狀的六維屬性總值——遵循心法 1 的 TLV 循環即可化解。
反面提醒：這份樣本解析成功，僅代表格式正確；欄位值是否越界、目標是否歸屬本人、當前狀態是否允許變更，仍必須由伺服器端在業務層獨立判定。

🛠️ 第七章：手把手撰寫 Wire 處理器 (*Wire.java 標準模板)

在伺服器端通訊層的 Wire 套件（本專案以 lmproject.lab.wire 這類自有命名空間組織）下開發任何協定處理器時，必須遵循以下標準工業範式：

package lmproject.lab.wire;

import java.util.Objects;

/**
 * 協議處理器標準範式：具備安全 Skip、順序無關、雙向容錯機制
 */
public final class ExampleWire {
    private ExampleWire() {}

    /**
     * 解碼客戶端 C2S 請求
     * 心法 1 & 2：欄位順序無關、語法有界的未知欄位跳過；
     * 但格式損毀與必要欄位缺漏一律 Fail-Closed。
     */
    public static ExampleRequest decode(byte[] data) {
        // 空 body 不是「安全」的預設值：突變型請求必須 Fail-Closed
        if (data == null || data.length == 0) {
            throw new WireDecodeException(REASON_EMPTY_BODY);
        }
        LmProto.Cursor cursor = new LmProto.Cursor(data);
        long targetId = 0;
        int actionType = 0;
        String memo = "";
        boolean sawTargetId = false;

        while (cursor.remaining() > 0) {
            long key = cursor.readVarint();
            long field = key >>> 3;
            int wireType = (int) (key & 7);

            switch ((int) field) {
                case 1:
                    if (wireType == 0) { targetId = cursor.readVarint(); sawTargetId = true; }
                    else cursor.skipWire(wireType);
                    break;
                case 2:
                    if (wireType == 0) actionType = (int) cursor.readVarint();
                    else cursor.skipWire(wireType);
                    break;
                case 3:
                    if (wireType == 2) memo = cursor.readString();
                    else cursor.skipWire(wireType);
                    break;
                default:
                    // 語法有界的未知 Tag：精確跳過，不中斷連線
                    // （若 skipWire 發現長度越界／WireType 非法，會自行拋出格式損毀例外）
                    cursor.skipWire(wireType);
                    break;
            }
        }
        // 必要業務欄位缺漏 → Fail-Closed，不可套用預設值
        if (!sawTargetId || targetId == 0L) {
            throw new WireDecodeException(REASON_MISSING_TARGET);
        }
        return new ExampleRequest(targetId, actionType, memo);
    }

    /**
     * 編碼伺服端 S2C 響應封包
     * 心法 3 & 4：輕量組裝、俄羅斯套娃嵌套封裝
     */
    public static byte[] encodeResponse(int statusCode, byte[] subPayload) {
        // 1. 組裝基本欄位
        byte[] field1 = LmProto.fieldVarint(1, statusCode);

        // 2. 組裝嵌套子結構 (俄羅斯套娃)：將子 bytes 作為 WireType 2 封裝
        byte[] field2 = (subPayload != null && subPayload.length > 0)
                ? LmProto.fieldBytes(2, subPayload)
                : new byte[0];

        // 3. 串接輸出
        return LmProto.concat(field1, field2);
    }
}

🔍 第八章：本地契約復原工具鏈與排錯方法論

1. 離線描述符目錄查詢 (local protobuf catalog)

由自持本地樣本的共用原生函式庫以唯讀靜態分析萃取的二進位協定目錄（如 *-protobuf-catalog.json）：

  • 收錄範圍為數千個 Message 與上萬個欄位（確切數量隨樣本版本浮動，實際數字請以當次本地萃取結果為準，勿引用本頁數字）。
  • 遇到未知 Opcode 時，先以此 JSON 搜尋 RTTI 符號或常數所對應的 Message 名稱。
  • 使用限制：目錄只提供「名稱 ↔ 欄位編號 ↔ WireType」的候選對應。欄位語意仍需以實驗室流量與離線合約測試交叉驗證後才能落地。

2. 伺服器端有界 Hex 診斷日誌 (world_frame_parse_reject)

所有協定解析失敗處均配置有界長度的 Hex 輸出（上限 24 bytes，避免日誌被單一封包灌爆）。當客戶端動作無反應時，先檢查控制台：

world_frame_parse_reject opcode=10 body_len=14 body_hex=120c0815100d18142009280a300b

拿到 body_hex 後，即可利用本指南第 2、6 章的規則進行人工逐位元反編譯。
藍側提醒：這類日誌同時是防守方最直接的觀測點——解析拒絕率、拒絕原因的分布、以及同一會話的重複拒絕次數，都應納入監控（見第十章）。

📝 第九章：快速自檢與實戰問答 (Quick Check & FAQs)

在著手開發前，請透過以下高頻情境確認自己已具備完整的底層心理模型：

Q1: 在 Protobuf 封包中讀到 Key = 0x08，請問它是幾號欄位？資料型態為何？
標準解析：
0x08 轉為二進位為 0000 1000。
低 3 位元為 000 = WireType 0 (Varint)。
高位右移 3 位（8 >> 3）為 1。
答案：Field 1, WireType 0 (Varint 整數/布林)。
Q2: 客戶端送來一個伺服器端沒定義過的未知 Tag 時，什麼情況可以跳過、什麼情況必須拒絕？
標準解析：
Protobuf 的 Key 自帶 WireType 資訊，若該欄位語法有界，解碼器能精確計算其位元組長度並安全跳過——這是格式相容性，不是安全保證。
但以下情形必須 Fail-Closed：
① 線格式損毀（長度越界、WireType 非法、Varint 未終止）；
② 必要業務欄位缺漏（不得套用預設值默默執行）；
③ 會話狀態不允許該動作；
④ 目標不屬於當前角色或動作超出權限。
一律斷線則是另一個常見錯誤：會把客戶端無害的本地暫存欄位誤判為攻擊，導致正常玩家被踢下線。
結論：WireType 層可以寬，業務與權限層必須嚴。
Q3: 什麼是「套娃」問題？組裝子結構封包時最常犯的重大錯誤是什麼？
標準解析：
Protobuf 沒有獨立的 Object 形態，子結構在二進位流中本質上是 WireType 2 的位元組區塊（套娃）。最常犯的重大錯誤是「漏套中間的盒子」——直接把最內層零件丟進最外層，缺少了中間層的 Tag 與長度前綴，導致客戶端 C++ 解析器判定格式損壞而整包丟棄，面板回退顯示舊資料。
Q4: 為什麼在本專案的實驗室環境中，使用自有的輕量 Wire 工具類優於 protoc 生成代碼？
標準解析：
protoc 會生成龐大的 Java 類別，在契約持續微調的開發階段，每次欄位變動都會觸發繁重的全量編譯；而輕量工具類直接操作位元組陣列，無額外物件配置負擔，欄位調整可即時生效並立刻補上合約測試。
Q5: 什麼是「最小合法注入原則」？為什麼絕對不能「腦補欄位」？
標準解析：
客戶端是預先編譯的 C++ 靜態結構。若伺服器端憑空猜測並下發客戶端未註冊的額外欄位，可能引發解析失敗甚至客戶端崩潰，也容易被防守方的封包形狀監控標記為異常。下發必須嚴格基於實驗室觀察（Golden Trace）證實的最小合法集合。

🛡️ 第十章：紅藍對照：本地契約復原如何決定伺服器防線

前面九章講的是「怎麼把二進位協定寫對」。本章補上一個常被忽略的視角：同一份客戶端契約，攻擊者與防守者都會去讀。因此，理解「本地契約復原」能走多深，直接決定了伺服器端哪些閘門不能省。

🚧 本章的證據邊界（先讀這段）

下表右側的藍側欄位是依據協定格式特性推導出的「應當可觀測」項目，屬於設計建議與待建檢查（proposed checks），不是已實際執行的攻擊、不是已完成的滲透測試結果，也不是本專案偵測到的入侵事件。本專案未對任何未授權的後端資料庫進行直接存取、寫入或外洩；本庫中的歷史封包擷取與唯讀觀測記錄僅用於理解協定格式，不能用來推論任何第三方系統的安全性。

10.1 紅側：證據受限的契約復原路徑

下表描述的是在自己持有的本地樣本上復原契約所需的最小步驟。它的價值不在「攻擊」，而在於它恰好是防守方必須假設已經被掌握的路徑——防守方不能指望「攻擊者看不懂協定格式」來提供安全邊界。

階段 動作 能取得什麼 證據強度
R1 本地樣本與中繼資料盤點 檔案雜湊、符號表、匯出函式名稱、內嵌字串與版本標記。這些都是檔案層級的中繼資料，不需要執行任何東西。 本地觀察（確定的靜態事實）
R2 離線描述符復原 「Message 名稱 ↔ 欄位編號 ↔ WireType」的候選對應，以及哪些欄位是巢狀的。可以看出結構，但看不出語意與合法值域。 本地觀察 + 推測（語意部分需另行驗證）
R3 自建實驗室流量觀察 在自建伺服器上，由自己控制的測試用戶端所送出的實際 frame：Opcode、長度、欄位出現順序與取值範圍。 本地觀察（僅覆蓋實驗室已實作的功能）
R4 構造差異請求 把已知欄位改成邊界值（負數、極大值、他人物件識別碼、重複欄位），觀察伺服器端如何反應。此列為理論上可做的差異測試類型。 假設性檢查；本頁沒有此類差異請求已執行的證據
R5 對照結果、修正契約 對已觀察的契約落差建立離線迴歸；其他邊界值測試應先取得自建環境的結果，再考慮補驗證。 已觀察案例可重現；其餘屬待驗證建議
⚠️ R4 的紅線

R4 僅可在自建實驗室、對自有服務端執行。把差異請求送向未獲授權的正式服務是越界行為；既有唯讀對照不等於已執行對外差異測試。本頁不提供規避偵測或取得他人資料的作法。
另請注意：邊界值檢查是為了驗證服務端不變量，預期越界請求被拒絕。

10.2 藍側：每一階段對應的可觀測性與建議檢查（proposed checks）

以下清單是建議應當存在的檢查與觀測點，屬於待建／待驗證項目；本專案未對任何第三方系統執行過這些檢查，也不以此主張任何既有環境的實際安全水位。

🔎 契約面（對應 R1–R2）

  • 最小注入稽核：確認下發欄位集合是最小合法集合，未夾帶推測欄位（心法 5）。
  • 契約版本對帳：客戶端更新時，比對描述符目錄差異，逐一確認新增欄位的語意與必要性。
  • 假設檢驗：把「攻擊者讀不到描述符」明確列為不成立的假設，不要讓它出現在威脅模型的「我們比較安全」欄位裡。

🧱 輸入面（對應 R3–R4）

  • 有界解析：巢狀深度、單封長度、陣列元素數都要設上限，防止資源耗盡。
  • 值域與型別檢查：即使 WireType 正確，欄位值仍須落在合法值域內（負數、溢出值一律拒絕）。
  • 跳過僅限語法有界者：只有在 WireType 讓長度可被精確計算時才跳過未知欄位；凡是長度越界、WireType 非法或游標無法對齊者，一律有界地拒絕該封包，不得放行。
  • Fail-Closed 四閘門：格式損毀、必要欄位缺漏、狀態不符、越權操作，全部拒絕並記錄（心法 2）。

🧭 業務面（授權與持有權）

  • 持有權檢查：所有作用於物件的操作，必須驗證物件歸屬當前會話；不可僅信任封包內攜帶的識別碼。
  • 狀態機閘門：交易中、騎乘中、死亡中、世界中未認證等狀態，分別定義允許的操作集合。
  • 速率與去重：同一 Opcode 的短時間高頻請求應觸發節流，抵禦「連續點擊」型壓力。

📡 可觀測性面

  • 解析拒絕率與原因分布：格式損毀、缺欄位、越權各自計數，異常上升即為訊號。
  • 每會話拒絕次數：短時間內大量重複拒絕是自動化嘗試的典型特徵。
  • 狀態否決日誌：記錄「因狀態／權限被拒」的動作，便於後續回溯。
  • 日誌衛生：Hex 輸出必須有界，且不得寫入憑證、token 或個人識別資訊。
✅ 為什麼「客戶端契約復原」決定伺服器防線

因為 Wire 上的欄位編號與線型別可以被觀察：持有本地樣本的人可透過描述符與受控流量逐步比對巢狀結構；欄位語意仍須獨立佐證。這意味著：

  • 「看不懂封包所以安全」不是可用的防線；
  • 格式相容性（能跳過未知欄位）與安全授權（能不能執行這個動作）是兩件不同的事，後者必須由伺服器端獨立判定；
  • 因此所有真正的安全邊界，都必須落在伺服器端的授權、狀態與持有權檢查上，而不是落在「格式難以偽造」這種假設上。

再次強調：客戶端面板顯示數值改變，僅代表渲染層收到並接受了資料，不代表伺服器端授權通過；權威狀態一律以伺服器端為準。
